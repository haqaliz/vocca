## 0. Open question 2, resolved: a first-responder override, not the tap and not a monitor

The PRD left this open and warned it could move the aspect's size. It does not. Three candidates:

| Candidate | Verdict |
|---|---|
| Divert the existing `CGEvent` tap while recording | **No.** The tap swallows what it takes, system-wide. A recorder stuck in the recording state would eat the user's entire keyboard, and the way out needs the keyboard. It also makes the recorder depend on the Accessibility grant |
| A global `NSEvent` monitor | **No.** Same swallow risk, wider than needed |
| **A first-responder override in our own window** | **Yes** |

`FailsafePanel` already does exactly this — `performKeyEquivalent(with:)` (`FailsafePanel.swift:192`)
and `keyDown(with:)` (`:203`) — to take ⌘C / ⏎ / ✕ inside a Vocca-owned window. The recorder is the
same shape: while it is first responder it sees `keyDown` and `flagsChanged` and consumes them;
everywhere else the keyboard is untouched.

It needs **no Accessibility grant**, **cannot** swallow keys outside our window, and **adds no seam
row**: `NSEvent` is already named in `VoccaUI/FailsafePanel.swift` and is governed by no seam table.

**One consequence to state honestly and not work around:** a chord the system claims first
(⌘Space with Spotlight enabled, ⌘Tab) may never reach our responder at all. The recorder must
therefore treat "nothing arrived" as *nothing arrived* — it cannot distinguish a stolen chord from
an unpressed one, which is the same wall `shortcut-conflicts` hit and the reason N1 stays deferred.
No inference may be built on the silence.

## 2. Implementation phases

### Phase 1 — The reducer (Core, pure)
`Sources/VoccaCore/HotkeyRecorderState.swift`: `HotkeyRecorderState`, a closed
`HotkeyRecorderAction`, and `HotkeyRecorderReducer.reduce(_:_:)`.

States: `idle` → `recording` → `idle` (accepted / refused(reason) / awaitingConfirmation(warning)).
Actions: `began`, `chordCaptured(HotkeyChord, HotkeyBindingValidity)`, `confirmed`, `cancelled`,
`rebindAnswered(RebindOutcome)`.

**No time-based transition exists in the action set** — the house rule (`AppsTabState`,
`WidgetStateReducer`). Pin it as a closed-set test.
**The reducer does not validate**; it is handed a `HotkeyBindingValidity` and shapes it. Validation
lives in `HotkeyBindingRules` and is not re-derived — the `AppsTabReducer` precedent of deferring
to Core's projections.
**Commit:** `Add the hotkey recorder's reducer and its decision table`

### Phase 2 — Copy, and the pin `SettingsCopy` has never had
`SettingsCopy.hotkeyNotRebindable` is **deleted** — it becomes false. New strings for: the record
button, the recording prompt, each refusal reason, the system-shortcut warning, the
mid-dictation refusal, and the sentence stating Vocca cannot see other applications' shortcuts.

**`SettingsCopy` has no byte-for-byte pin test today** (PRD R5) — grep finds `hotkeyNotRebindable`
only in three unrelated doc comments, so deleting it is a change nothing would notice. Add
`Tests/HarnessTests/SettingsCopyTests.swift` pinning **every** `SettingsCopy` string, plus a scan
asserting `hotkeyNotRebindable` survives nowhere in `Sources/`.
**Commit:** `Say what the hotkey is, and what Vocca cannot see`

### Phase 3 — The live display name (M10)
`SettingsBindings.hotkeyDisplayName` becomes `() -> String`. Today it is a plain `String`
(`SettingsView.swift:24-152`) captured once, while the window is built once and kept for the
process lifetime (`AppBootstrap.swift:1031-1035`) — so after a rebind it would show the old chord
until relaunch.

The **menu bar** (`MenuBarItem(hotkey:)`, `AppBootstrap.swift:519-520`) and **onboarding**'s
"Hold ⌥Space" copy carry the same defect and are fixed here. All three render through
`HotkeyChordFormatter` — one formatter, no second dialect.
**Test:** reading the closure twice across a rebind returns two different values; and the
three-surface agreement test (the `settings-live-controls` precedent that caught the stranded-
OPENING defect).
**Commit:** `Show the chord that is actually bound, everywhere it is shown`

### Phase 4 — The recorder view + wiring
`Sources/VoccaUI/Settings/HotkeyRecorderView.swift` — thin glue over the reducer, with an
`NSView`/panel-level `keyDown`/`flagsChanged` override per §0. Escape aborts; clicking away aborts.
`SettingsBindings` gains `rebind: (HotkeyChord) -> RebindOutcome`, wired to
`DictationLoopRoot.rebind(to:)` in `showSettings()`.
**Executed by nothing in CI** (window-server precedent) — the reducer, the copy pins and the
agreement test are the tested half.
**Commit:** `Let a person record a new hotkey`

### Phase 5 — Floor. **Commit:** `Raise the suite floor for the hotkey recorder`

## 3. Acceptance criteria (from `spec.md`)

1. Reducer decision table, one test per transition: Escape aborts from `recording` leaving the
   binding untouched; a refused chord returns to `idle` with the reason and persists nothing; a
   warned chord requires an explicit confirm.
2. **No time-based transition exists** — closed-set test over the action enum.
3. Copy pinned byte-for-byte; `hotkeyNotRebindable` exists nowhere in `Sources/`.
4. **The three surfaces never disagree** — tab, menu bar, onboarding, all through one formatter.
5. **A stale chord is impossible after a rebind** — asserted over the binding closures, not the view.
6. A mid-session rebind attempt surfaces `.refused(.sessionInFlight)` rather than silently no-op'ing.

Pins (2, 4, 5) must be proven by planting: add a timed action; give the menu bar its own formatter;
restore `hotkeyDisplayName` to a stored `String`.

## 4. Failure behaviour

| Case | Behaviour |
|---|---|
| Chord never arrives (system claimed it) | recorder stays in `recording` until Escape or click-away. **No inference from silence** (§0) |
| `rebind` returns `.refused(.sessionInFlight)` | shown in the tab; recorder returns to `idle`; nothing persisted |
| `rebind` returns `.refused(.notBindable)` | shown with the reason; this should be unreachable, since the reducer already refused — assert it as a defensive path, do not rely on it |
| Accessibility not granted | the recorder still works (it is first-responder, not the tap). The *hotkey* will not fire, which the menu bar already reports |
