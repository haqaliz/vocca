# Implementation plan: `rebind-boundary`

**Unit:** `hotkey-rebinding` · **Aspect:** `rebind-boundary` · **Date:** 2026-08-30
**Sources:** `prd.md` (M4, M4a, M5), `rebind-boundary/spec.md`
**Prerequisites:** `binding-vocabulary` (`7a4dfa4`), `binding-store` (`7879262`) — floor 1551

> **This aspect carries the unit's only Fatal-rated risk (PRD R1 / roadmap C1-A, "stuck
> recording").** Everything below is arranged around making the failure unrepresentable rather
> than unlikely.

---

## 0. Open question 1 is now answered: the tap is never re-armed

The PRD said to confirm this against the code rather than assume it. Confirmed:

- `ModeRoutingSink` is built once in `DictationLoopRoot.init` (`AppBootstrap.swift:1527`) and held
  as a `private let` (`:1372`). Only its `.active` field changes.
- The tap-health graph is built **on the routing sink, not on a wiring**:
  `TapHealthPolicy(source: tap, sink: modeRouting, …)`. Nothing in it names `holdToTalk` or
  `toggle`.
- `handleSessionCancelKey` reads the computed `activeWiring`, not a captured one — so Escape
  routing follows a rebuild for free.

**So a rebind re-points `modeRouting.active` and nothing else touches the tap.** Re-arming it would
be actively wrong: `CGEvent.tapCreate` needs the Accessibility grant, and a needless re-create is a
chance to lose a working tap for no gain.

## 0.1 What must change shape

`holdToTalk` and `toggle` are `public let` (`:955`, `:958`). They become `public private(set) var`.
That is the only mutability this aspect adds, and it is on the root — **not** on
`HotkeyConfiguration`, **not** on `SessionMachine.configuration`. Every value stays immutable;
what changes is which immutable object the root points at. That distinction is the whole safety
argument (PRD §5.1).

---

## 1. The central design move: one factory, two callers

`DictationLoopRoot.init` builds the two `Wiring`s inline. If `rebind` builds them a second time
inline, the two constructions **will** drift — and a rebuilt wiring that differs from a launched
one is a bug that only appears after a rebind, which is the hardest kind to see.

**Extract the construction into one private factory** — `makeWirings(chord:) -> (hold: Wiring,
toggle: Wiring)` — and have `init` and `rebind` both call it. A test asserts the two paths produce
equivalent wirings for the same chord.

Each `Wiring` needs `configuration, ceiling, clock, source, keyState, timer, deferOpening,
deliverEffect` (`AppBootstrap.swift:883-892`). All but `configuration` and `timer` are the root's
own long-lived collaborators and are reused. **`timer` must be fresh per wiring** — a
`RepeatingTimer` handed to a new `ScheduledWatchdog` while the old one still holds it is two
owners on one timer, and the old owner is about to be discarded.

---

## 2. The order of operations, and why each step is where it is

```
rebind(to chord:) -> RebindOutcome
  1. guard chord != current                      -> .unchanged
  2. guard HotkeyBindingRules.validate adoptable -> .refused(.notBindable)
  3. guard hold.machine.state == .idle
        && toggle.machine.state == .idle         -> .refused(.sessionInFlight)
  4. build BOTH new wirings (fallible/expensive work happens here, nothing adopted yet)
  5. settings.setHotkeyChord(chord)              (persist)
  6. swap holdToTalk / toggle; re-point modeRouting.active   <- one synchronous block
  7. stop the two old timers
  return .rebound
```

- **Step 3 checks *both* machines, not the routed one.** Both are constructed at every launch and
  a session in the unrouted machine is still a session. This is the load-bearing guard.
- **Steps 4 and 5 are in this order, deliberately deviating from `setActiveMode`.** That method
  persists before adopting because its adopt is infallible. Ours does real construction first, so
  persisting first would risk a store describing a chord the running app never adopted — the exact
  failure `setActiveMode`'s own comment warns about, arrived at from the other direction.
- **Step 6 must contain no `await` and no suspension point.** The whole method is `@MainActor` and
  synchronous; a suspension between the idle check and the swap would let a session start into a
  wiring about to be discarded. **Do not make `rebind` `async`.**
- **Step 7 is after the swap**, so a failure to stop an old timer cannot leave the new graph
  unrouted. Old-timer teardown must respect `DeinitIsolationTests`: a `deinit` may call only
  `tearDown` / `stopWithoutAssertingIsolation` / `deallocate`. `MainRunLoopTimer.stop()` asserts
  main-actor isolation and is **not** compiled out at `-O` — this is the fourth place that rule
  has mattered.

**Atomicity (M4a) falls out of the ordering:** nothing is adopted until step 6, and step 6 is a
straight-line assignment block. There is no window in which one wiring is new and the other old,
and none in which `modeRouting.active` points at a discarded object.

## 2.1 The outcome type

```swift
public enum RebindOutcome: Sendable, Equatable {
    case rebound
    case unchanged
    case refused(RebindRefusal)
}
public enum RebindRefusal: Sendable, Equatable, CaseIterable {
    case sessionInFlight, notBindable
}
```
**Returned, not merely logged** (M5) — the Speech tab's model-removal shape
(`SpeechTabState.swift:297`), not activation mode's silent no-op. `CaseIterable` so the
exhaustiveness test can iterate it.

## 3. Implementation phases

1. **Extract the factory.** `makeWirings(chord:)`; `init` uses it. *No behaviour change* — the
   test is that `configure` still produces today's two configurations. **Commit:**
   `Build the two wirings in one place, so a rebuild cannot drift`
2. **The outcome vocabulary.** `RebindOutcome` / `RebindRefusal`. **Commit:** `Name what a rebind
   can answer`
3. **`rebind(to:)`** per §2. **Commit:** `Rebind on an idle boundary, without mutating a running
   session`
4. **Floor.** **Commit:** `Raise the suite floor for the rebind boundary`

## 4. Testing strategy — acceptance criteria from `spec.md`

| # | Test |
|---|---|
| 1 | **refused while a session is in flight**, driven over the closed set of non-`.idle` states for **each machine independently** — hold busy/toggle idle, and the mirror. The load-bearing test |
| 2 | after success: both machines carry the new chord; exactly one wiring routed; the routed one matches `activeMode`; both `.idle` |
| 3 | after a **failed/refused** rebind: the previous configuration is still live, exactly one wiring still routed, and the outcome says why — driven for each refusal case |
| 4 | a no-op rebind returns `.unchanged` and rebuilds nothing — asserted by **object identity** of both wirings, not by state |
| 5 | persist happens only on success — a refused rebind leaves the store untouched |
| 6 | **the tap source is the same object across a rebind** — identity, not equality |
| 7 | a chord `HotkeyBindingRules` refuses is rejected before anything is persisted or built |
| 8 | **the new chord starts a session and the old one does not** — end to end through the machine over a fake `HotkeyEventSource`. The behavioural proof, not just the wiring proof |
| 9 | `init` and `rebind` produce equivalent wirings for the same chord (the §1 drift guard) |
| 10 | `modeRouting.active` points at the **new** wiring's `scheduledWatchdog`, for both activation modes |

**Pins must be planted to be trusted.** For 1, 4, 6 and 10, plant the defect (drop one machine from
the idle guard; rebuild on a no-op; re-create the tap; re-point at the old wiring), watch it fire,
remove the plant, report what it said.

Commands: `./Scripts/test-with-floor.sh`; then `swift build --build-tests` with zero warnings.

## 5. Failure behaviour

| Case | Behaviour |
|---|---|
| Rebind during a dictation | refused, session untouched, reason returned. **Never** interrupts |
| Rebind with a chord the rules refuse | refused before persist or build |
| Persist fails | best-effort, never throws (seam contract). The rebind still adopts, so the change works now and is lost on relaunch — better than refusing a change the user can see took effect |
| Old timer fails to stop | new graph is already routed; a leaked timer is a leak, not a dead hotkey |

**The failure this aspect exists to prevent:** a graph with no routed sink. On an `LSUIElement`
app a dead hotkey is indistinguishable from a working one — the class behind three
`fix/local-dev-launch` defects. Criterion 3 asserts the post-condition after *every* attempt,
successful or not, which is the only way that failure becomes visible to CI.

---

## 6. Agent execution notes

- One agent, sequential. Phase 1 must be a **pure refactor** with the suite green before Phase 3
  begins; if Phase 1 changes any observable behaviour, stop and report rather than proceeding.
- **Ask before proceeding if** a `Wiring` collaborator turns out to be captured by something built
  before it (which would make the swap non-atomic), or if `rebind` cannot be written synchronously.
- **Do not** add a setter to `HotkeyConfiguration` or `SessionMachine.configuration`. **Do not**
  make `rebind` `async`. **Do not** re-create the tap. **Do not** touch any UI.
