## 0. Two corrections to the spec, before any code

### 0.1 The safe single-key set in the spec is wrong, and would break text editing

`binding-vocabulary/spec.md` names the safe set as *"F1–F20, Home, End, Page Up, Page Down,
**Forward Delete**, Help, and the keypad keys"*. That list was lifted, unexamined, from the shape of
`HotkeyFlagTranslation.keyCodesCarryingFunctionImplicitly`
(`Sources/VoccaHotkey/HotkeyFlagTranslation.swift:126-144`) — which exists to answer a **different
question**: "which key codes does macOS set the `fn` bit on by itself?"

Those two questions have different answers. Binding is global and swallowing, so a safe key must be
one nobody needs while typing:

| Key | In the fn table | Safe to bind bare? | Why |
|---|---|---|---|
| F1–F20 | yes | **yes** | Not text entry, not navigation. This is what the accessibility case wants |
| Home / End / Page Up / Page Down | yes | **yes, with a note** | Navigation, but not per-keystroke; a user who binds one has chosen to lose it |
| **Forward Delete** | yes | **NO — remove** | An *editing* key. Swallowing it globally breaks deleting text, in a tool whose entire job is putting text into fields |
| **Arrow keys** | yes | **NO — never include** | Per-keystroke navigation. Swallowing an arrow makes every text field unusable. They were never in the spec's list; naming them here so nobody adds them later by pattern-matching the fn table |
| Help | yes | yes | Vestigial on modern keyboards |
| Keypad keys | **no** | yes | Numeric duplicates; a keypad `5` is a distinct key code from a main-row `5` |

**Action:** the safe set is **F1–F20, Home, End, Page Up, Page Down, Help, and the keypad keys.**
Forward Delete is removed. This is a correction to `spec.md` and is made in the same commit.

### 0.2 The set must not be derived from the fn table, and the two must be pinned apart

They overlap by construction but mean different things, and they live in different modules
(`VoccaCore` decides; `VoccaHotkey` translates — `ModuleBoundaryTests` forbids Core importing the
adapter anyway). Duplicating the literals is correct here; **silently letting them drift into
agreement is not.** A test asserts the intended difference explicitly: Forward Delete and the four
arrows are in the fn table and **not** in the safe set. Without it, a later well-meaning
"deduplicate these two tables" commit re-introduces §0.1's bug with a green suite.

### 0.3 A prior decision this aspect must not re-litigate

`ModifierSet.swift` already documents the founder's decision at the end of `session-lifecycle`:
`fn` stays bindable, and `VoccaHotkey` strips it for key codes that carry it implicitly. It also
already carries the worked table of how a bare `F13` binding fails in both directions if that is
got wrong. **So the bare-F13 case already works today at the event layer.** This aspect adds the
*validity* decision, and must configure a bare F13 as modifiers `[]` — matching what the adapter
delivers after the strip. Getting this backwards produces a binding that never fires.

## 2. Implementation phases

Each phase is RED → GREEN → REFACTOR. **No production code before a failing test.**

### Phase 1 — The refusal vocabulary and the validity answer

- **Goal:** the closed answer type and reason set exist, with nothing deciding yet.
- **Prerequisites:** none.
- **Files:** create `Sources/VoccaCore/HotkeyBindingValidity.swift`.
- **Shape:**
  ```swift
  public enum HotkeyBindingValidity: Sendable, Equatable {
      case accepted
      case warned(HotkeyBindingWarning)
      case refused(HotkeyBindingRefusal)
  }
  public enum HotkeyBindingRefusal: Sendable, Equatable, CaseIterable {
      case modifierOnly, reservedByVocca, unmodifiedTextEntryKey
  }
  public enum HotkeyBindingWarning: Sendable, Equatable {
      case usedBySystemShortcut(name: String?)   // filled by `shortcut-conflicts`
  }
  ```
  `HotkeyBindingRefusal` is `CaseIterable` **so the exhaustiveness test can iterate it** — that is
  the mechanism behind acceptance criterion 1, not decoration.
- **Validation:** `swift build`; a test asserting every `HotkeyBindingRefusal` case is reachable
  fails RED (nothing produces them yet).
- **Commit:** `Name what makes a hotkey binding illegal`

### Phase 2 — The safe single-key table

- **Goal:** one named table, and the pin that keeps it apart from the fn table.
- **Files:** create `Sources/VoccaCore/HotkeyBindingTables.swift`.
- **Contents:** `safeUnmodifiedKeyCodes: Set<UInt16>` per §0.1, each entry commented with its
  `kVK_*` name, values read individually from `Carbon/HIToolbox/Events.h` — **not extrapolated**,
  the same warning `HotkeyFlagTranslation` carries, because the F-keys are not contiguous there
  (`kVK_F17` is `0x40` while `kVK_F16` is `0x6A`). Also `textEntryKeyCodes` — the letters, digits,
  punctuation, Space, Return, Tab, Delete/backspace — and `escapeKeyCode` re-declared? **No:**
  Escape's code lives in `SessionKeyPolicy.escapeKeyCode` (`VoccaHotkey`), which Core cannot
  import. Declare it here as the Core-side source of truth and add a test asserting the two agree,
  rather than a second silent literal.
- **Validation:** tests for criteria 3, and the §0.2 difference pin.
- **Commit:** `Name the keys a person can bind without a modifier`

### Phase 3 — The decision function

- **Goal:** `HotkeyBindingRules.validate(keyCode:modifiers:) -> HotkeyBindingValidity`, pure.
- **Files:** create `Sources/VoccaCore/HotkeyBindingRules.swift`.
- **Order of checks, and it matters:** mask `.locking` → `modifierOnly` → `reservedByVocca` →
  unmodified? → safe-set member ⇒ `accepted`, else `unmodifiedTextEntryKey`. Escape is checked
  **before** the unmodified test so that `⌘Escape` is refused as `reservedByVocca` rather than
  accepted as a modified key (criterion 4).
- **Validation:** criteria 1, 2, 4, 5, 6, 8 all green.
- **Commit:** `Decide whether a chord may be bound`

### Phase 4 — The chord formatter

- **Goal:** one renderer every surface uses.
- **Files:** create `Sources/VoccaCore/HotkeyChordFormatter.swift`.
- **Contents:** modifiers in the platform's canonical order `⌃⌥⇧⌘` (`fn` before them, as macOS
  renders it), then the key name from a table. Unknown key codes render as `Key <n>` rather than
  empty — a nameless chord is still better than a blank control.
- **Validation:** criterion 7, including the **byte-for-byte match with
  `AppBootstrap.shippedHotkeyDisplayName == "⌥Space"`**, so the menu bar's string does not change
  on the day it starts coming from here.
- **Commit:** `Render a chord the way a person reads it`

### Phase 5 — Single-source scans and the floor

- **Goal:** the tables cannot acquire a second home; the floor reflects reality.
- **Files:** modify `Tests/HarnessTests/HotkeyBindingRulesTests.swift`; modify
  `Scripts/test-with-floor.sh`.
- **Note on the scan:** the `StrategyMemoryTargets` shape scans for a **literal**. That is wrong
  here — `0x69` legitimately appears in both `HotkeyBindingTables` and `HotkeyFlagTranslation`.
  Scan for the **table's identifier** (`safeUnmodifiedKeyCodes`) instead, asserting it is declared
  in exactly one file and read only where expected. Say so in the test's doc comment so the
  deviation from the house pattern is deliberate and legible.
- **Validation:** `./Scripts/test-with-floor.sh` green at the new floor.
- **Commit:** `Pin the binding tables to one home each`

## 4. Testing strategy

Lifted from `spec.md`'s acceptance list; not re-invented.

| Criterion | Test | Note |
|---|---|---|
| 1 | every `HotkeyBindingRefusal` case is produced by some candidate | iterates `allCases`, so a new reason without a test fails |
| 2 | **every** unmodified text-entry key is refused | drives the whole table, not a sample — this is the bricking guard |
| 3 | **every** safe key is accepted unmodified | drives the whole table |
| 4 | Escape refused under all 32 modifier combinations | Vocca's cancel must not become conditional |
| 5 | modifier-only refused, per modifier and all combinations | |
| 6 | `⌃⌥D` accepted | the refusal is about *unmodified*, not about text keys |
| 7 | formatter table, incl. `⌥Space` byte-for-byte vs the shipped constant | |
| 8 | Caps Lock never changes an answer | each case run with and without the bit |
| 9 | table-identifier scans; §0.2 difference pin | |

**Commands:** `swift build`, then `./Scripts/test-with-floor.sh`. Never bare `swift test` — it
exits 0 on discovering nothing, which is the whole reason the floor script exists.
**Clean build for the final check**, not incremental: incremental builds hide warnings in unchanged
files, and CI fails on any warning under strict concurrency.

**Nothing here needs the network, a microphone, a window server, TCC, or a model.** This is one of
the rare aspects fully provable in CI — the `rules-engine` precedent.

## 6. Edge cases & failure behaviour

| Case | Behaviour |
|---|---|
| Key code above the real keyboard range | not in any table ⇒ `unmodifiedTextEntryKey` if unmodified, `accepted` if modified. Deliberate: refusing unknown modified codes would block legitimate non-US layouts and unusual keyboards |
| Keypad `5` vs main-row `5` | distinct codes; keypad accepted, main row refused. **Asserted explicitly**, because assuming they share a code is the obvious mistake |
| `fn` as the only modifier on an F-key | the adapter strips implicit `fn` before this is ever asked (§0.3); the candidate arrives as `[]` and is judged by the safe set |
| Caps Lock present in a candidate | masked before every check, both sides, per `ModifierSet.locking` |
| Unknown key code in the formatter | renders `Key <n>`, never empty |

**Failure mode of the aspect as a whole:** it is a pure function with no I/O, so it cannot fail at
runtime. Its failure is being *wrong* — and the two wrong answers have very different costs.
A false `refused` is an annoyance the user can work around. A false `accepted` on a text-entry key
makes that key untypeable system-wide, with the recovery path behind a Settings window that needs
the keyboard. **The tests are therefore written to be exhaustive on the refusal side and merely
representative on the acceptance side.**

## 7. Agent execution notes

- **One agent, sequential.** The five phases are strictly dependent (types → tables → rules →
  formatter → pins); there is no independent work to fan out, so parallel dispatch would only
  create merge conflicts in one module.
- **Checkpoint for human review after Phase 2** — the safe-key table is a judgement call the PRD
  records as R3, and §0.1 already corrected it once. Worth a human eye before it hardens.
- **Ask before proceeding if:** the Escape key code declared in Core disagrees with
  `SessionKeyPolicy.escapeKeyCode`, or if `AppBootstrap.shippedHotkeyDisplayName` cannot be matched
  byte-for-byte by the formatter — both indicate a wrong assumption, not a test to adjust.
- **Do not** import `VoccaHotkey` from `VoccaCore` to reuse the fn table. `ModuleBoundaryTests`
  forbids it, and §0.2 explains why the duplication is correct.
- **Update `spec.md`'s safe-set line** in the same commit as Phase 2, per §0.1.
