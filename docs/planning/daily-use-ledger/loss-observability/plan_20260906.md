## Decisions this plan makes

Both were left open by the spec; both are resolved by reading the code rather than by preference.

**1. `.lost` carries no payload.** Site 4 (`DictationPipeline.swift:376`) is reachable exactly one
way — the ladder returned `.widgetFailsafe` and `holder.current()` was `nil`. There is one cause,
so a `reason:` payload would carry a constant. A second loss path arriving later is a
compiler-guided change at that point. Simpler shape wins, per the spec's stated bias.

**2. The case is named `lost`.** It reads correctly at the call site (`outcome: .lost`), in
`describe()` (`session 3: lost, …`), and in a counter (`day.lost`). The doc comment names the
cause; the case name names the consequence — which is what the gate counts.

---

## The RED test, and why it does not name `.lost`

The obvious first test — assert site 4 yields `.lost` — **cannot compile** before the case exists,
and a compile error is not a RED test. Adding the case first to make it compile would be
production code before a failing test.

So the RED test asserts **the defect itself**, in terms that compile against the tree as it stands
today:

```swift
// Compiles today. Fails today. Passes only once the two are distinguishable.
XCTAssertNotEqual(
    outcomeOfFailsafeWithNoCustody, outcomeOfTranscribeFailure,
    """
    A transcript that reached the failsafe and was refused custody is recorded under the same \
    outcome as a transcription that never produced anything. The P0 gate counts transcript loss \
    at exactly zero (ROADMAP.md:96), and this makes that count uncomputable: the failure that \
    lost a transcript is indistinguishable from the failure that had none to lose.
    """)
```

`SessionOutcomeClass` is `Equatable` (`SessionOutcomeClass.swift:22`), so this compiles now,
fails now for exactly the right reason, and cannot pass by accident. It also does not presuppose
the fix's shape — any honest separation satisfies it.

## Testing strategy

Every test is headless, deterministic, and network-free — the pipeline suite drives doubles, never
a real engine or injector, so nothing here can touch a model or the network. No fixture audio is
needed: these routes are reached by making a double throw or return `nil`, not by transcribing.

- **Unit:** phases 1 and 3 above.
- **Integration:** none new. The zero-network probe already exercises the delivered route
  end-to-end; `.lost` is not on that path.
- **Regression watch:** `ZeroNetworkTests` parses the `PROBE-LATENCY` line
  (`ZeroNetworkTests.swift:580-640`). It asserts *grammar and record count*, not a fixed outcome
  spelling, and the probe's cycle delivers rather than losing — so adding a case should not touch
  it. **Verify, don't assume:** if that suite goes red, the cause is the describe() grammar and the
  fix belongs in the same commit.
- **Manual:** none. Nothing user-visible changes in this aspect.

## Edge cases and failure behaviour

| Case | Behaviour |
|---|---|
| The holder returns `nil` **and** the ladder delivered on a real rung | Unreachable — the `nil` check is inside the `.widgetFailsafe` arm only. No change |
| A future second loss path appears | The compiler does not force it to be `.lost`; A6's single-site scan is what catches a second one appearing without a decision. This is deliberate — a new loss site should be a reviewed edit |
| `.lost` is mistaken for a user-visible change | It is not. The widget still presents `.exhausted` at site 4; the notice text, the failsafe behaviour and the surface are all untouched |
| The floor is ratcheted to a predicted rather than an observed number | Forbidden — read it from the run. A wrong floor either hides a shrinking suite or fails CI for nothing |

## Agent execution notes

- **Checkpoint after Phase 1.** The RED must fail for the stated reason. An agent that reports
  "test written, suite green" has written the wrong test — the whole aspect rests on this failing
  first.
- **Phase 2 is deliberately tiny.** One enum case, one changed line, one switch arm, plus whatever
  the compiler names. An agent proposing to refactor the pipeline's error routing has exceeded the
  aspect.
- **Ask before proceeding if:** the RED test cannot be made to fail without touching production
  code; or `ZeroNetworkTests` goes red in Phase 2 (that means `describe()`'s output is pinned more
  tightly than this plan assumes, and the pin's location should be confirmed before editing it).
- **Do not** rename `failed`, and do not reclassify sites 1, 2, 3, 5 or 6. Their adjudication is
  recorded in the spec with each site's own code comment as evidence.
