## 1. What ships

`Sources/VoccaActions/Providers/AuditActionProvider.swift` — an **actor** conforming to
`ActionProvider`, over the `FileSystemActionAuditStore` already in this module.

| Tool | Blast radius | Behaviour |
|---|---|---|
| `audit.count` | `readOnly` | How many entries the audit log holds |
| `audit.clear` | `destructive` | Clears the audit log — irreversible |

**Why this provider, in one line for the doc comment:** `VoccaActions` declares exactly
`["VoccaCore"]` (asserted by equality) and `ModuleBoundaryTests` rule 3 forbids an adapter
importing any other Vocca module, so the audit store is the one real capability reachable from
here without a boundary violation or an injection layer this slice does not need.

## 2. ⚠️ The ordering question this aspect must pin

**Clearing the audit log is itself an auditable action.**

- Record the clear **before** clearing → the clear erases its own trace; the log reads empty and
  looks untouched.
- Record the clear **after** clearing → the log reads "cleared", surviving as ordinal 1.

**The second is correct, and must be asserted rather than assumed:** after `audit.clear`, the
log is **not empty** — it holds exactly one entry, the record of its own clearing. A log that
can be silently emptied by an action is not an audit log.

Write the reasoning into the doc comment. A future reader seeing "clear leaves one entry" will
otherwise read it as a bug.

**Note the layering:** the provider performs the clear; the *gate's* caller writes the audit
entry. So the provider must clear and report, and the entry lands after — which is the natural
order, but assert it end-to-end rather than trusting it.

## 3. Phases

### Phase 1 — RED

**File:** `Tests/HarnessTests/AuditActionProviderTests.swift`

1. Exposes exactly two tools, with the declared blast radii (`CaseIterable`-style sweep over the
   tool list, so a third tool added later fails here first).
2. `audit.count` returns the **real** entry count — driven against a real store over a temp
   directory with a known number of entries written first. Non-empty domain.
3. `audit.count`'s **summary is concrete** — it names the count. This is the requirement that
   forced `describe` async; assert the number appears.
4. `audit.clear` empties the log **and leaves exactly one entry: the record of the clear** (§2).
5. **The real-provider refusal.** `audit.clear` submitted through `ActionGate` without a
   confirmation is refused, and the log is **unchanged** — slice 1's load-bearing test, run
   against a real provider for the first time rather than a stub.
6. **Dry-run leaves the log byte-identical.** Read the directory's bytes before and after;
   compare. This is the strongest available form of "zero side effects" and is only assertable
   now that a real provider exists.
7. `audit.count` runs directly on the read-only path with an enabled tool and no token.
8. An unknown tool id returns a refusal summary / `.failed`, never a trap.

**Commit.** `audit-provider: pin the AuditActionProvider contract — RED against a provider that does not exist`

### Phase 2 — GREEN

**File:** `Sources/VoccaActions/Providers/AuditActionProvider.swift`

- An `actor` holding the store. Conformance witnesses are `async` (this is why `async-seam`
  shipped first).
- Concrete summaries: `audit.count` → the count; `audit.clear` → the count that will be deleted,
  and that it is permanent.
- Unknown tool → a refusal summary and `.failed(reasonKey:)`, never a trap.
- Apache-2.0 header. Strict concurrency, zero warnings.
- **The transport lint must stay green** — this file names no transport and no subprocess.

**Commit.** `audit-provider: the AuditActionProvider — the second real implementation behind the seam (GREEN)`
