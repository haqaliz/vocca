Ships: the persisted per-mode selection shape (`cleanup-config.json` grows one key), the
mode-scoped `CleanupResolver`, the Cleanup tab's converse picker (one control), the honest
doc-comment updates that say what `CleanupContext.mode` now means, the contract tests, the
wiring scans, and the floor ratchet.

Does NOT touch: **`DictationPipeline.swift`** — byte-for-byte pinned by the G5 digest
(`TurnTakingComposedAcceptanceTests.swift:317-347`; digest `ce70ca10…`). The dictate path's
mode is `.dictation`, which is exactly what the pinned `cleanIfWired` already hard-codes
(`DictationPipeline.swift:442,468-470`) — so the consumption happens where the per-mode
selection is read: the resolver. The pin stands; this plan contains zero edits to it. Does NOT
touch `SessionMachine.swift` (pinned) or `AppBootstrap.swift` (pinned; re-anchored once, by
`converse-wiring` — this aspect's one new binding is defaulted and its shipped wiring is a
recorded handoff to that aspect). Does NOT wire the converse loop (that is `converse-wiring`;
this aspect supplies it `resolve(mode: .conversing)` and stops). Does NOT touch the four
providers' internals (`ShippingCleanup.swift`, `BYOKCleanupProvider.swift`,
`OllamaCleanupProvider.swift`, `ChainedCleanupProvider.swift` — all mode-agnostic, all
unchanged). Does NOT change the timeout-yields-raw / never-block machinery (the race is the
caller's, pinned by `DictationPipelineTests.swift:854-881`; this aspect only guarantees the

## Design decisions (made here, recorded)

**D1 — The persisted per-mode selection shape: one new key in `cleanup-config.json`, no
migration.** The existing `provider` key keeps its on-disk spelling and its meaning — it is
now explicitly the **dictate** mode's selection. The new key is `converseProvider`, carrying
the same three raw strings (`rules|ollama|byok`, byte-pinned by `CleanupProviderKind.swift:33-39`).
- An existing file (no `converseProvider`) decodes to converse `.rules` **silently**: the
  converse path's default is the zero-network rung (the PRD's G7 posture), and old files need
  no migration because the dictate half is byte-identical to today.
- Unknown `converseProvider` string ⇒ converse `.rules` + exactly one loud log (the hand-edit
  doctrine, `CleanupConfig.swift:57-66`).
- **The one deliberate semantic change to the degrade policy, tested**: an invalid **selected
  converse** block (e.g. `converseProvider: byok` with an undialable endpoint) degrades **only
  the converse selection** to rules — the dictate selection stands. Today's rule ("invalid
  selected block ⇒ whole config to rules", :244-256) still applies to the dictate half, pinned
  unchanged. Two independent selections cannot keep a shared "one invalid block kills both"
  rule without making a byok dictate user lose their choice to a typo in the converse block
  they never edited.
- **Why the file, not UserDefaults**: the selection needs the ollama/byok blocks beside it,
  the tab already reads and writes exactly this file (`CleanupSummaryTests.swift:170-185`),
  the "applies at next launch" semantics already exist for it, and the resolve-once doctrine
  means the file is read at most once per launch regardless. `UserDefaults` stays for
  launch-path scalars.
- Storage: `CleanupConfigDraft` (VoccaCore) gains `converseProvider: CleanupProviderKind`
  (default `.rules` — zero churn at existing construction sites); `CleanupConfig` (VoccaText)
  gains the same defaulted field, plus the `draft`/`init(draft:)` translation and the
  `encoded()`/`tolerantDecode` legs. `CleanupConfigStore` is shape-agnostic — unchanged.

**D2 — The resolver becomes per-mode; the dictate path keeps today's behavior exactly.**
- `resolve(mode: SessionMode)` is new; the no-arg `resolve()` becomes
  `resolve(mode: .dictation)` — same decision table, same degrade, same cache. The pipeline's
  acquisition (`AppBootstrap.swift:503`), the egress fold (:556-559) and the tab's summary
  binding (:1353-1354) all call no-arg forms and are byte-for-byte unaffected — no pinned file
  moves.
- **One file read total, both providers built in the one flight**: the single-flight guard
  holds a `(dictation, conversing)` pair; the first resolve (either mode) reads the file once
  and builds both halves. The B4 pin (`CleanupResolverTests.swift:41-86`) holds even when both
  modes are resolved — `fileExists == 1`. Never-swap holds **per mode**: a mid-session swap is
  structurally impossible for each half, which is the dictation-era doctrine extended honestly
  (`CleanupResolver.swift:23-26` doc updated).
- The converse half runs the identical `build()` decision table over `converseProvider`, with
  the per-mode degrade of D1. `summary()`/`egressEndpoint()` keep dictation semantics (no-arg);
  `summary(mode:)`/`egressEndpoint(mode:)` are added for the converse surface and
  `converse-wiring`.
- The caller still constructs `CleanupContext(mode:)`: the pinned pipeline passes `.dictation`
  (its hard-coded value is the truth), `converse-wiring` passes `.conversing`. **The mode is
  consumed at the resolver seam — provider selection by mode — not by providers.** The
  timeout-yields-raw guarantee is untouched: the race lives in the caller
  (`DictationPipeline.swift:439-466`); this aspect only pins that each per-mode provider keeps
  its declared `budget`/`requiresNetwork`, so the caller races the same numbers as today.

**D3 — The Cleanup tab surface: one control — the converse rung picker.** A second Section,
"While conversing", under the existing one, reusing the same three rung rows
(`rungName`/`rungDetail`/`rungEgressNote`), the same `fields(for:)` editors, and the same byok
confirmation dialog. Nothing about the existing picker changes.
- `CleanupTabState` gains `converseSelection: CleanupProviderKind` (default `.rules`),
  `converseRows` (derived by the same pure `rows(selection:draft:)` — the function takes a
  selection value and doesn't care which mode it is), and `converseSummary: CleanupSummary?`.
  `.configLoaded` moves both selections from the draft. New action `.converseSaveSucceeded(kind)`
  is "the only action that moves the converse selection" — a parallel of the existing doctrine
  (`CleanupTabState.swift:168-173`).
- `plan(_:picking:mode: SessionMode = .dictation)` — the defaulted parameter keeps every
  existing call site compiling; the refuse→confirm→write ladder is identical, applied to the
  draft's `provider` or `converseProvider` half.
- The confirmation flow must know which picker is pending: `pendingConfirmation` becomes a
  small `CleanupPendingConfirmation { kind: CleanupProviderKind, mode: SessionMode }` struct
  (VoccaUI, `Sendable`/`Equatable`), and `.confirmationRequested` gains the mode. Existing
  construction sites in `CleanupTabReducerTests`/`CleanupCloudConfirmationTests` are updated
  mechanically in the same commit as the shape change — named there, never silent.
- The "Using" line stays the dictate provider's (today's copy, today's meaning). A converse
  "Using" line renders only when the new defaulted binding `cleanupConversingSummary`
  (default `{ nil }` — the house "defaults claim nothing" discipline,
  `SettingsView.swift:172-179`) answers non-nil. **Recorded handoff**: wiring that one binding
  is one additive line in `converse-wiring`'s AppBootstrap re-anchor commit — this aspect
  makes no AppBootstrap edit, so the pin is re-anchored exactly once, by the aspect whose PRD
  owns it (G6, `prd.md:73-79`).
- Copy, decided here and pinned by `CleanupTabCopyTests`:
  `converseSectionTitle = "While conversing"`;
  `converseSectionDetail = "The cleanup that runs on what you say to Vocca — nothing from a
  conversation is ever typed into an app."` (the never-injects prohibition, R2, stated on the
  surface that would otherwise read as "cleanup for the other thing").

**D4 — The honest record of what the mode field now means.** Four doc comments updated in the
GREEN commit, none in a pinned file:
- `SessionMode.swift:17-21` — "Declared, never read at C5" becomes: read since C11 at the
  cleanup resolver; the mode selects the cleanup provider; the pinned pipeline constructs
  `.dictation` contexts; `converse-wiring` constructs `.conversing`.
- `CleanupContext.swift:24,38-39` — the same: the mode is consumed at the resolver seam; a
  conformer may read it, no provider branches on it.
- `CleanupResolver.swift:19-26` — "one cleanup provider for the process" becomes "one provider
  per mode, resolved from one file read, resolve-once per mode".
- `CleanupConfig.swift:50-66` — the file's two selections and the per-mode degrade rule.
