## 1. The constraint that decides the shape

**`VoccaCore` imports no Foundation.** Verified: `grep -n "import Foundation" Sources/VoccaCore/*.swift`
returns zero hits, and `CoreBoundaryTests.testVoccaCoreImportsOnlyWhatIsExplicitlyPermitted`
enforces it. So `UserDefaults` **cannot** live in Core, and neither can `JSONEncoder`. `Codable` is
stdlib and is fine, but is not needed here.

The split is therefore forced, and it is the house pattern anyway — Core owns the decision, the
adapter owns the naming:

| Layer | Module | Holds |
|---|---|---|
| Vocabulary + decision | `VoccaCore` | the stable string identifiers, and the **pure** tolerant decode |
| Adapter | `VoccaUI` | the one file naming `UserDefaults`, beside `CompletionFlagStore` |

`VoccaUI` is where `CompletionFlagStore` already lives and is already read from `main()` by the
composition root, so a settings store read at launch has a precedent in the same module.

## 2. Findings that change the spec's assumptions

Two corrections from the persistence dig, both making this aspect *easier* than `prd.md` assumed:

1. **The UserDefaults lint has no exact-set-count pin.** Unlike the FileManager table — pinned at
   exactly four by `testTheFileManagerSeamTableNamesExactlyTheFourShippedSeams` — the UserDefaults
   family (`InjectionSeamBoundaryTests.swift:1453-1594`) is a tree-wide scan over a table with one
   row and **no count assertion**. Adding a second seam is a new table row plus a file that really
   names `UserDefaults`; there is no hard-coded number to bump.
2. **`VoccaASR` is not a scanned root of the FileManager lint at all.** It already names
   `FileManager` in three files (`ModelStore`, `ModelDownloader`, `DefaultModelTransport`) that sit
   outside the four-seam table's per-module scope. Irrelevant to this aspect's implementation —
   we are not putting the store there — but it is a real hole in the lint and is recorded here so
   it is not rediscovered as a surprise.

## 3. The identifier decision — do not overload

Aspect 1 existed because one string carried two meanings. **Do not add a third meaning to
`EngineTier.storageID`.** A settings key and a directory name answer different questions and change
for different reasons: a directory name is a fact about an artifact on disk, a settings key is a
fact about a file we must keep decoding forever.

Introduce a separate `persistedIdentifier` on the persisted types, pinned byte-for-byte by test, so
a Swift case rename can never silently reset a user's choice (spec R5).

## 4. Phases

### Phase 1 — RED: the vocabulary and its tolerant decode (pure, in Core)

**Files:** `Sources/VoccaCore/PersistedSettings.swift` (new),
`Tests/HarnessTests/PersistedSettingsTests.swift` (new).

Tests, each written failing first:
1. Every `EngineTier` and every `DictationMode` has a `persistedIdentifier`, and the values are
   pinned **byte-for-byte as literals** — not derived from the enum, which would pass through any
   rename (the `testTheParakeetPathIsUnchangedByTierKeying` lesson from aspect 1).
2. Identifiers are pairwise distinct across each type — the aspect-1 uniqueness lesson, applied
   before the defect rather than after.
3. Round-trip: `decode(persistedIdentifier(x)) == x` for every case, driven over `allCases` so a
   new tier cannot be added without an identifier.
4. **Tolerant decode:** an absent value yields the shipped default; an unknown string yields the
   shipped default **and reports the invalid input** through a callback (the
   `FileSystemDictionaryStore.decode(_:onInvalidElement:)` precedent — a pure function cannot log,
   so the caller does).
5. The decode is **pure and Foundation-free** — assert `VoccaCore` still imports nothing new by
   leaving `CoreBoundaryTests` green.

**Commit:** `Add the persisted-settings vocabulary and its tolerant decode`

### Phase 2 — RED: the UserDefaults adapter, and the lint row

**Files:** `Sources/VoccaUI/Settings/UserDefaultsSettingsStore.swift` (new),
`Tests/HarnessTests/UserDefaultsSettingsStoreTests.swift` (new),
`Tests/HarnessTests/InjectionSeamBoundaryTests.swift` (one table row).

Follow `CompletionFlagStore` exactly: a plain struct over an **injected** `UserDefaults`
(`.standard` by default, a scoped `UserDefaults(suiteName:)` in tests, purged with
`removePersistentDomain` in a `defer` — the user's real defaults must be untouchable). Synchronous
reads, never throwing.

Tests:
1. A written engine selection reads back; a written activation mode reads back.
2. Absent ⇒ shipped defaults (`EngineSelection.defaultSelection`, `AppBootstrap.defaultMode`'s
   value — do not import Bootstrap; pin the value).
3. **Malformed value ⇒ shipped default AND a loud report.** Assert the *loud* half, not just the
   fallback — a silent reset is the failure mode this rule exists for.
4. The store never writes on a failed read (the dictionary store's rule: a bad load must not
   rewrite the file).
5. **The lint still bites:** a planted second `UserDefaults`-naming file fails the seam scan. The
   existing planted-tree negative control covers the mechanism; confirm the new row did not
   loosen it.

**The lint row** to add at `InjectionSeamBoundaryTests.swift:1453`-ish:
```swift
"settings": ["VoccaUI/Settings/UserDefaultsSettingsStore.swift"],
```
Ships **in the same commit** as the file that needs it — the process `CompletionFlagStore` itself
followed and documented.

**Commit:** `Persist the engine selection and activation mode behind a UserDefaults seam`

## 5. Scope boundaries (do not cross)

- **Do NOT wire anything into `AppBootstrap`.** The five `.defaultSelection` read sites, the
  resolver, and the `activeMode` constant are **aspect 3**. This aspect ships a store that nothing
  reads yet, exactly as the seam-first house discipline intends.
- **Do NOT touch any UI page.** Aspects 4 and 5.
- **Do NOT migrate `CompletionFlagStore`.** The PRD leaves it open; moving it risks the `main()`
  show decision for no gain in this aspect. Record the decision, change nothing.
- **Do NOT put the cleanup provider choice here.** It stays in `cleanup-config.json`, which is
  hand-editable by design (aspect 5).

## 6. Edge cases and safe failure

| Case | Required behaviour |
|---|---|
| Absent key (fresh install) | Shipped default, **no log** — this is the normal path, not an error |
| Unknown identifier (downgrade, hand-edit) | Shipped default **plus** a loud report; never a crash, never a silent reset |
| Value of the wrong type in defaults | Same as unknown identifier |
| Two processes writing | Out of scope — Vocca is single-instance; do not build coordination for it |

**Failure posture:** every failure here degrades to the shipped default, which is a working
configuration. Nothing in this aspect can make Vocca unusable, and nothing may throw into a caller
that has no way to recover.
