## 2. Corrections carried in from aspect 2

Aspect 2's plan asserted `DictationMode` lives in `VoccaCore`. **It does not** — it is
`AppBootstrap.swift:736`, and `VoccaUI` may import only `VoccaCore`. Aspect 2 therefore persisted
`HotkeyConfiguration.Activation` (`Sources/VoccaCore/HotkeyConfiguration.swift:41`), which is the
type `SessionRules.decide` and `SessionWatchdog` already branch on. That was the right call and
stands.

**The debt it left, which this aspect pays:** `PersistedSettings.defaultActivation = .toggle`
(`PersistedSettings.swift:122`) duplicates `AppBootstrap.defaultMode = .toggle`, held closed only
by a test-only pin. **R5 below collapses it** — `defaultMode` derives from the Core constant, and
the duplication and its pin go away. Two constants agreeing by test is a worse state than one
constant, and it exists only because aspect 2 could not reach the root.

## 3. The design decision this plan commits to

Three things must change together, and the order matters.

**(a) `EngineReadiness` stops being a one-way latch.** A switch must be able to *close* the gate
again — the engine that was ready is not the engine now selected. Add an explicit transition back
to not-ready.

> **Safety argument, and read this before touching it.** Closing the gate is always safe: a closed
> gate refuses a press with an honest `.modelUnavailable` notice and the microphone never opens.
> Opening it wrongly is the unsafe direction, and nothing here opens it — `markEnginePrepared()`
> remains the only opener and is still reached only after `prepareIfNeeded()` succeeds. Preserve
> that. A test must pin that no new path opens the gate.

**(b) The resolver becomes replaceable, via a box.** `DictationEngineResolver.selection` is a
`let` with no reset path (by design — resolve-once). So a switch **builds a new resolver**. But
`pipelineAssembly` is a closure handed to the root from `configure`, capturing the resolver from
`configure`'s scope — a rebuilt resolver would leave the closure calling the dead one.

Use the house pattern already in this file: a shared mutable box (`rootBox`, `sessionBox` are the
precedents). `configure` creates a `ResolverBox`, the assembly closure reads
`resolverBox.value` **at call time**, and a switch swaps the box's contents. Do **not** capture a
resolver instance in any long-lived closure.

**(c) A `preparing` state, distinct from `unavailable`.** PRD M11: the in-between window must not
look like a failure. `.modelUnavailable` currently means both "no model" and, after a switch,
"model is right there but not warm yet" — and the second is not a failure, it is a wait.

## 4. Phases

### Phase 1 — RED: readiness becomes two-way, and nothing new opens the gate

**Files:** `AppBootstrap.swift` (`EngineReadiness`), `Tests/HarnessTests/EngineReadinessTests.swift` (new or extend).

Tests first:
1. A readiness marked ready and then marked preparing reads **not ready** — the gate re-closes.
2. Both gates (`gate`, `toggleGate`) see the change, since they share one instance — drive both.
3. **The closed set of openers:** `markEnginePrepared()` is the only path that sets ready. Assert it
   over the type's surface so a future addition has to change this test deliberately.
4. A closed gate refuses `beginCapture` with `.unavailable` and leaves the machine healthy —
   existing behaviour, pinned here because this aspect is where it could break.

**Commit:** `Let engine readiness close again, without adding a way to open it`

### Phase 2 — RED: the selection is read from the store at all five sites

**Files:** `AppBootstrap.swift` (`:196, :206, :208, :355, :937`),
`Tests/HarnessTests/EngineSelectionWiringTests.swift` (new).

Tests first:
1. A store holding Whisper ⇒ the root resolves the whisper identity; an empty store ⇒ Parakeet.
2. `defaultSelection` is reached **only** on an empty/invalid store — drive the invalid case too.
3. All five sites agree: the manifest, the base URL, the onboarding presence check and the
   settings display name all describe the **same** selection. A test that pins only the resolver
   would miss exactly the class of bug where the download session fetches one engine's model while
   the resolver builds another.

**Commit:** `Read the engine selection from the store at every site that had hardcoded it`

### Phase 3 — RED: switching, at the next session boundary

**Files:** `AppBootstrap.swift` (the `ResolverBox`, `setEngineSelection(_:)`),
`Tests/HarnessTests/EngineSwitchTests.swift` (new).

`setEngineSelection(_:)` follows `setActiveMode`'s shape exactly (`:1277-1291`):
guard idle → persist → swap the box → close readiness → **eagerly prepare** → on success install the
pipeline and open the gate.

Tests first:
1. A change while a session is in flight is **refused and logged**; the running session's
   `engineIdentity` is unchanged. (Both machines idle is the guard — check `holdToTalk` and
   `toggle`, as `setActiveMode` does.)
2. A session started *after* a change resolves the **new** engine — no restart. This is C3's
   acceptance criterion (`CAPABILITY_ROADMAP.md:81`).
3. **R3/M10 — eager prepare:** a switch triggers `prepare()` on the newly selected engine exactly
   once, with no press. Assert the count, not just that it happened.
4. The assembly closure calls the **current** resolver after a swap, never the replaced one.
5. A switch persists — a simulated relaunch reads the new selection.

**Commit:** `Switch engines at the next session boundary, preparing the new one eagerly`

### Phase 4 — Activation mode from the store, and the duplication collapsed

**Files:** `AppBootstrap.swift` (`activeMode`'s initial value, `defaultMode`),
`Sources/VoccaCore/PersistedSettings.swift` (doc comment), `PersistedSettingsTests.swift` (retire the pin).

1. `activeMode` reads the persisted activation at launch instead of the constant (`:888`).
2. `setActiveMode` persists.
3. **`AppBootstrap.defaultMode` derives from `PersistedSettings.defaultActivation`**; the
   duplicate literal and its test-only agreement pin are deleted, since the thing they guarded
   no longer exists.
4. Activation survives a simulated relaunch.

**Commit:** `Persist the activation mode, and collapse the duplicated default`

### Phase 5 — The `preparing` state, and the contract that was untrue

**Files:** the readiness/reason surface, `Tests/HarnessTests/EngineSelectionConsumptionTests.swift` (doc comment).

1. With a switch in flight, the reported state is **preparing**, not **unavailable**, and the two
   are distinguishable in whatever projection the UI and menu bar read.
2. **R6:** `EngineSelectionConsumptionTests.swift:24-27` documents *"No restart needed … nothing
   about it is cached at launch."* That was true of the pure function and false of the wired app.
   It is true now — rewrite the comment to say what actually makes it true.
3. The zero-network probe stays green; `PROBE-CYCLE`/`PROBE-LATENCY` unchanged for the default
   configuration.
4. Ratchet `Scripts/test-with-floor.sh:1185` from 1375, plus its dated log paragraph.

**Commit:** `Report preparing as its own state, and make the no-restart contract true`

## 5. Out of scope

Any settings page (aspects 4, 5). Any new latency claim — the C7 warm-start bound covers the
**launch** path only, and this aspect must not imply a post-switch warm-start number (PRD R-F).

## 6. Edge cases and safe failure

| Case | Required behaviour |
|---|---|
| Switch while a session is in flight | Refused + logged; running session untouched (`setActiveMode` precedent) |
| Switch to an engine whose model is absent | Gate stays closed; next press refuses honestly with `.modelUnavailable`. This is correct, not a bug |
| `prepare()` fails after a switch | Gate stays closed, reason surfaced intact, selection **stays switched** — the user asked for it; do not silently revert |
| Switch during an in-flight preparation | Single-flight must not be broken: the older preparation must not open the gate for the newer selection. **This is the sharpest hazard in the aspect** — pin it |
| Store unreadable at launch | Shipped defaults, loud log (aspect 2's behaviour, already tested) |

## 7. Agent execution notes

- **Checkpoint after Phase 1.** Readiness is a safety mechanism; a mistake there opens a microphone
  that should be shut.
- **The sharpest hazard is Phase 3's stale-preparation race** — an in-flight `prepareIfNeeded()`
  for the OLD resolver completing after a swap and calling `markEnginePrepared()`. The box swap
  alone does not prevent it. Handle it explicitly and pin it with a test.
- **Ask before proceeding** if the assembly closure cannot be made to read the box at call time
  without restructuring `DictationLoopRoot`'s initializer — that is a design question.
- Do not weaken any existing test to make a new one pass. If an existing test contradicts this
  plan, stop and report: it may be pinning something this plan got wrong.
